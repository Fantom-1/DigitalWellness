GROUND-ZERO
Implementation Plan — Overview & Roadmap
Feasibility Review, Scope Cuts, and Phased Delivery Plan
Prepared for Yash Khedekar  |  July 2026  |  v1.0

1. What This Document Is
The original concept doc describes Ground-Zero correctly at the philosophy level: a Wikipedia + IMDB + PCPartPicker for AI models, not a model host or inference proxy. That framing is sound and should not change. What needs to change is the assumption, implicit in the original doc, that all of it gets built at once. It does not. This document cuts the idea down to a buildable v0.1, sequences the rest, and flags every place where the original spec is more ambitious than a solo or 2–3 person team can execute in a semester.
Bottom line:  The idea is good and the moat argument (data + provenance + explainability, not UI) is correct. The risk is not the concept — it's sequencing. Build the boring parts (schema, ingestion, one connector) before the exciting parts (ranking engine, LLM intent parsing).
2. Reality Check on the Original Spec
Before planning modules, here is a direct assessment of the claims and structures in the source document.
2.1 What's solid
Layered architecture (ingestion → normalize → DB → search/rank → frontend) is the correct shape and matches how real data-aggregator products (PCPartPicker, similarweb, G2) are built.
PostgreSQL + pgvector + JSONB is the right database choice for this problem. You get relational integrity for the 90% of fields that are structured, JSONB for the long tail of source-specific fields, and vector search for semantic ranking, all in one engine — no need for a separate vector DB (Pinecone/Weaviate/Qdrant) at this scale.
Wikipedia-style proposal → review → merge contribution model is the correct trust mechanism, and version history + verification levels is what makes the data defensible long-term.
"LLM used once, for intent parsing, everything else deterministic" is the right cost and reliability posture. This keeps inference cost near-zero per search and keeps ranking explainable and debuggable.
2.2 What's underspecified or unrealistic as written
"Continuously ingest from HuggingFace, Ollama, OpenRouter, GitHub, official labs, and papers" is 5 connectors before v1 ships. Each connector needs its own auth, rate-limit handling, schema mapping, and dedup logic. Realistic v0.1 scope is one connector (HuggingFace Hub API — by far the richest metadata source) plus manual seeding for 50–100 flagship models.
The ranking formula ("Final Score = Intent Match + Hardware Match + Capability Match + Cost Match + Freshness + Popularity + Community Trust + Official Verification + Benchmark Score") has 9 terms with no defined weights, scales, or normalization. As written this is a slogan, not an algorithm. Section 4 of the Ranking Engine document fixes this with a concrete, tunable formula.
Natural-language intent parsing ("Need a coding model under 12GB VRAM" → structured filters) needs a fallback path for when the LLM mis-parses or the user's query has no clear intent. The original doc doesn't address failure modes; this is added in the Search Engine document.
"Daily update database, serve from local DB" is right for cost and latency, but a fixed daily cron for every source is wasteful (some sources like OpenRouter pricing change hourly; some like a paper's citation count barely move weekly). Recommend per-source refresh intervals, not one global scheduler cadence.
There is no comparison engine in the original doc, despite the PCPartPicker analogy implying one (PCPartPicker's core loop is side-by-side spec comparison). This is added as its own module because it reuses the ranking engine's normalized scores and is a natural v0.2 feature, not v0.1.
No mention of authentication, moderation roles, or abuse handling for the community contribution system. A public edit-suggestion system without spam/abuse controls will get gamed within weeks of any real traffic (fake benchmark numbers, self-promotional model entries). Addressed in the Contribution & Versioning document.

14. Migration Strategy
Use Alembic (Python, pairs with FastAPI) for schema migrations — not raw SQL files. Every schema change is a versioned, reversible migration.
Seed data (Phase 0's 30–50 flagship models) ships as a separate idempotent seed script, not baked into migrations — keeps schema history clean and re-runnable in any environment.
Never delete a model row on ingestion mismatch; set status = 'retired'. Hard deletes break every FK'd child table's history and any external links users may have bookmarked.

2.2 Response contract
Every field on a model detail response carries its verification_level and source alongside the value — not as a separate call. Every other connector in the original list (Ollama, OpenRouter, GitHub, papers) is deferred to Phase 4+.

Change from original:  The original doc proposes one "Daily" cadence for the whole pipeline. 4. Normalization Layer
4.1 Canonical ID resolution
The hardest real problem in this module is not fetching data — it's deciding whether two records from different sources (or two records from the same source in different runs) refer to the same model.
Slugify the incoming name (lowercase, strip punctuation, collapse whitespace to hyphens).
Check for exact slug match against existing models.
If no exact match, run a trigram similarity check (pg_trgm) against existing slugs/names above a similarity threshold (start at 0.85, tune from false-positive rate).
If still no match, check known alias table (many models have shipped under 2–3 names — e.g. a paper name vs. a productized name) before creating a new record.
Only create a new canonical model record if all three checks miss.
Risk flagged:  Fuzzy matching alone will misfire on legitimately distinct models with similar names (e.g. different size variants). Treat trigram match as a candidate flag for human review in early phases, not an auto-merge trigger, until the alias table has enough real-world coverage to be trusted.
4.2 Field-level merge policy
When two sources disagree on a field (e.g. HuggingFace says one license string, the official site says another), the normalizer does not silently overwrite. Policy:
Higher verification_level always wins (official > verified > community > experimental).
Equal verification_level → keep both in the sources/provenance table, surface the conflict as a flagged field for manual review, and keep the most recently captured value as the displayed value in the interim.
Never let an ingestion job silently overwrite a field that a human maintainer manually verified within the last 90 days — write a conflict record instead.
5. Validation Layer
Runs between normalization and DB write. Rejects or flags:
Missing required fields (slug, name, category).
Nonsensical numeric values (negative VRAM, release_date in the future, parameter_count of 0).
Broken/unreachable URLs for website, repository, and paper links (checked async, doesn't block the write, but flags the field as needing attention).
Duplicate slug collisions (should be impossible given §4.1, but validated defensively anyway).
6. Scheduler
APScheduler is sufficient for one connector at Phase 1–2 scale; migrate to Celery + Redis only once there are 3+ connectors or the ingestion volume needs distributed workers. Don't adopt Celery on day one — it's infrastructure overhead the v0.1 scope doesn't justify.

7. Auth (v0.1 minimal)

=== 03_Ground-Zero_Search_Engine.docx ===
GROUND-ZERO
Search Engine Module
Structured Filters, Full-Text Search, Semantic Layer, Intent Parsing
Module 3 of 7  |  v1.0

1. Design Principle
The original doc's search pipeline (sentence → intent parser → structured query → SQL filters → semantic ranking) is directionally correct and is kept. The change is making the structured filter UI a first-class, default input mode — not just a byproduct of parsing natural language.
Why this matters:  Natural language search is a nice-to-have, not the primary interface, for this product's actual users: ML practitioners who already know they want "open-weight, offline, under 12GB VRAM, good at code" and would rather click 4 filters than type a sentence and hope the parser gets it right. Ship the filter UI as the default; layer natural language on top.
2. Three-Tier Search Architecture
Tier
Mechanism
Handles
1. Structured filters
Direct SQL WHERE clauses on indexed columns
Category, capability, license, VRAM, price range, offline/online — the majority of real queries
2. Full-text search
Postgres tsvector on name + description + tags
Free-text queries like "reasoning model" or a partial model name
3. Semantic search
pgvector cosine similarity on description embeddings
Fuzzy intent like "something like GPT-4 but cheaper" or queries with no keyword overlap
Tier 1 always runs first and narrows the candidate set. Tiers 2 and 3 only re-rank within whatever Tier 1 already allowed through. This mirrors the original doc's "SQL filters first, semantic ranking after" instruction and is the right call — semantic search over the whole catalog with no filtering wastes compute and produces worse results than filter-then-rank.
3. Intent Parsing (Natural Language Input)
3.1 Pipeline
User query (free text)  -> LLM call (Claude Haiku, low-cost, single call)  -> Structured JSON: {task, offline, max_vram_gb, license, sort}  -> Validate against known enum values  -> If valid: run as Tier 1+2+3 pipeline  -> If invalid/low-confidence: fall back to full-text search on raw query
3.2 Fallback handling (missing from original spec)
The source doc shows the happy path only. Three failure modes must be handled explicitly:
LLM returns a filter value that doesn't map to any known enum (e.g. invents a category) — drop that filter, keep the rest, log for review.
LLM call itself fails or times out (API outage, rate limit) — fall back immediately to Tier 2 full-text search on the raw query string. Never block the search on the LLM being available.
Query has no extractable intent (e.g. "asdf" or a single ambiguous word) — return full-text + semantic results ranked by popularity, don't return an empty state.
Cost note:  One Haiku call per free-text search is inexpensive at low-to-medium traffic, but cache aggressively: identical or near-identical queries (case/whitespace-normalized) should hit a query-cache table before calling the LLM again.

=== 04_Ground-Zero_Ranking_Engine.docx ===
GROUND-ZERO
Ranking Engine Module
Scoring Formula, Weight Calibration, Explainability, Anti-Gaming
Module 4 of 7  |  v1.0

1. Fixing the Original Formula
The original doc's formula — Final Score = Intent Match + Hardware Match + Capability Match + Cost Match + Freshness + Popularity + Community Trust + Official Verification + Benchmark Score — names good signal categories but defines no weights, no scale, and no normalization. Nine unweighted terms summed together means whichever term happens to produce the largest raw numbers dominates by accident, not by design. This is not a ranking algorithm yet; it's a list of ingredients.
v0.1 fix:  Cut to 4 terms with explicit weights and a defined 0–100 scale per term. Ship this, collect real usage signal, then expand back toward the full 9-term model in v0.2+ once there's data to calibrate the additional weights against — guessing weights for Popularity or Community Trust with zero usage data is worse than not including them yet.
2. v0.1 Formula (4 terms)
final_score = (0.40 * intent_match)            + (0.25 * hardware_match)            + (0.20 * cost_match)            + (0.15 * freshness) -- all terms normalized to a 0-100 scale before weighting
Term
Weight
Definition
intent_match
0.40
Capability + task alignment: does this model do what the user asked for, and how well (uses the capabilities.proficiency field from the DB schema)
hardware_match
0.25
How well the model's min/recommended VRAM+RAM fits the user's stated or inferred hardware constraint; 100 if comfortably fits, scaled down as it approaches the ceiling, 0 if it doesn't fit at all
cost_match
0.20
Inverse-scaled against the user's stated budget or a sensible default ceiling if none given; free/local models score 100 by definition when offline was requested
freshness
0.15
Recency of release_date and last_verified_at, log-decayed — a 2-year-old model isn't worthless, just decayed
2.1 Why these four and in this order
Intent match is weighted highest because a fast, cheap, fresh model that can't do the task is useless — correctness gates everything else.
Hardware match outweighs cost because for the "offline coding model" persona this product is designed around, a model that doesn't fit in VRAM isn't a worse option, it's not an option.
Benchmark score is deliberately excluded from v0.1's formula, not because it's unimportant, but because benchmark comparability across models requires the benchmark_definitions normalization from Module 1 to actually be populated and trustworthy first — wiring in noisy/incomparable benchmark numbers as a scored term risks producing rankings that look precise but are actually garbage-in-garbage-out. Show benchmark scores on the model detail page in v0.1; don't rank by them yet.
3. v0.2+ Expansion (Restoring the Full 9-Term Model)
Once real usage data exists (click-through on results, "report incorrect" volume per field, actual benchmark coverage), reintroduce the remaining terms with data-informed weights rather than guesses:
Term
Planned v0.2+ weight
Prerequisite before enabling
benchmark_score
0.10 (redistributed from others)
benchmark_definitions table populated for ≥70% of catalog with official/verified-level scores
community_trust
0.05
Enough contribution volume (Module 7) to compute a meaningful trust signal per model, not per empty table
official_verification
folded into intent_match as a multiplier, not a separate additive term
Avoids double-counting — verification level already gates which value is displayed (Module 1 §4.2), so it shouldn't also double as an independent score term
popularity
0.05, capped influence
Explicitly capped low and monitored — see §5, Anti-Gaming
4. Explainability
Every ranked result carries a human-readable breakdown, not just a final number — this is explicitly called for in the original doc's design ("Explain Ranking" step) and is preserved as a hard requirement, not an optional nice-to-have.
{  "model": "llama-4-scout",  "final_score": 87,  "breakdown": [    {"term": "intent_match", "score": 92, "weight": 0.40, "reason": "Strong coding capability (4.5/5), task match"},    {"term": "hardware_match", "score": 85, "weight": 0.25, "reason": "Fits comfortably in 8GB VRAM at Q4"},    {"term": "cost_match", "score": 100, "weight": 0.20, "reason": "Free, runs locally"},    {"term": "freshness", "score": 70, "weight": 0.15, "reason": "Released 4 months ago"}  ]}
The frontend renders this as a short plain-language sentence per result ("Ranked #1 because it fits your 8GB VRAM, is free, and scores well for coding"), not the raw JSON — see Module 6.
5. Anti-Gaming (Missing from Original Spec)
The original doc doesn't address what happens when the catalog gets real traffic and real contributors, some acting in bad faith. This is not optional to think about — any public, community-editable ranking system will be targeted (self-promotion, competitor sabotage, fake benchmark submissions) within weeks of getting visible traffic.
Popularity, if/when added, must be based on aggregate, hard-to-fake signals (search-result click-through over time, not raw "views") and capped in weight (0.05 max as noted above) specifically because raw popularity is the easiest signal to manipulate.
Community-submitted benchmark scores or capability ratings are never immediately live — they enter as pending proposals (Module 7's review workflow) and only affect ranking after maintainer approval or reaching a minimum corroboration threshold from multiple independent contributors.
Rate-limit and fingerprint anonymous "report incorrect data" submissions per Module 2 §7 to prevent submission flooding from skewing the community_trust signal once it exists.
Log every ranking result set server-side (query, candidate set, final order, weights used at that time) so any future "why did model X suddenly rank higher" investigation is answerable from data, not guesswork.
6. Cold-Start Problem (Missing from Original Spec)
At launch, most models will have zero community signal, sparse benchmark coverage, and unverified hardware numbers pulled only from a single source. The ranking formula must degrade gracefully, not just work well once the catalog matures.
Missing terms are excluded from the weighted average and the remaining weights are re-normalized to sum to 1.0, rather than treating a missing value as 0 — a model with no cost data shouldn't be penalized as if it costs infinity.
Every model detail page and result card shows a small "data completeness" indicator (e.g. 6/9 fields verified) so users can calibrate their own trust in a thin ranking rather than being misled by false precision.
7. Weight Tuning Process (Post-Launch)
Instrument click-through and "was this helpful" feedback on search results from week one, even before there's enough data to act on.
After ~4–6 weeks of real usage, review whether top-ranked results are getting clicked/used, or whether users are consistently scrolling past the #1 result to pick #3 or #4 — the latter is a strong signal a weight is miscalibrated.
Adjust weights incrementally (no more than ±0.05 per term per iteration) and re-measure — avoid large swings based on small sample sizes.

Side-by-Side Model Diffing (New Module, v0.2)
Module 5 of 7  |  v1.0

1. Why This Module Exists
The original doc positions Ground-Zero as "the Wikipedia + IMDB + PCPartPicker for AI models" but never designs a comparison feature, despite PCPartPicker's entire core loop being side-by-side spec comparison to justify a build decision. This module fills that gap. It is scheduled for v0.2 (Phase 4 in the Overview roadmap) because it depends on two things v0.1 doesn't yet have: a reasonably deep catalog (comparing 2 of 30 models is a much weaker feature than comparing 2 of 2,000) and the Ranking Engine's normalized 0–100 scores to make the comparison meaningful rather than just a raw spec dump.
2. Core Interaction
User selects 2–4 models (from search results, a model detail page's "compare" button, or a direct /compare?ids= URL).
Comparison view shows every shared field side by side: capabilities, hardware requirements, pricing, license, benchmarks, ranking sub-scores.
Differences are visually highlighted (not just listed) — the value that's better in a given row is marked, using the same normalized scale the Ranking Engine already computes, so "better" isn't a separate subjective judgment invented by this module.
3. Data Requirements

4. API Design
GET /compare?ids=llama-4-scout,mistral-small-3,qwen3-14b {  "models": [...],  "fields": [    {"field": "min_vram_gb", "values": {"llama-4-scout": 8, "mistral-small-3": 12, "qwen3-14b": 16},     "best": "llama-4-scout", "direction": "lower_is_better"},    {"field": "intent_match_score", "values": {...}, "best": "qwen3-14b", "direction": "higher_is_better"}  ]}
direction (lower_is_better / higher_is_better) is stored per field type centrally, not guessed client-side — avoids the frontend incorrectly highlighting a lower price as "worse" or a higher VRAM requirement as "better."
5. Recommendation Delta
Beyond a raw diff table, the comparison engine generates one short plain-language recommendation sentence using the same deterministic scoring already computed — no additional LLM call needed for this, keeping it fast and free to run:
Example output:  "Qwen3 14B scores highest for your stated coding task, but needs 16GB VRAM vs. Llama 4 Scout's 8GB. If hardware is the binding constraint, Llama 4 Scout is the better fit despite the lower intent-match score."
This sentence is templated, not freely generated: pick the highest-scoring model overall, identify the single largest trade-off dimension (usually hardware or cost) against the next-best alternative, and fill a fixed sentence template. Keeps output predictable and cheap; avoids LLM hallucination risk in a comparison that's meant to be trustworthy.
6. Constraints & Scope for v0.2
Max 4 models per comparison — more becomes an unreadable table on both desktop and (especially) mobile.
No comparison across incompatible categories (e.g. comparing an LLM to a diffusion image model) — the UI should warn and suggest same-category comparison, since most fields wouldn't be comparable anyway.
Comparison URLs are shareable/bookmarkable (ids in query string) — this is a natural, high-value SEO and sharing surface ("Llama 4 Scout vs Mistral Small 3" is exactly the kind of query people search for) and should be server-rendered for that reason, not a client-only SPA route.
7. Explicit Non-Goals for This Module
Not a general "build your own filter table" pivot-table tool — that's a different, more complex feature with unclear demand; comparison stays fixed to the fields already modeled.
Not a benchmark-running service — Ground-Zero indexes and displays benchmark results, it never runs models or benchmarks itself, consistent with the original doc's "never host, never proxy inference" philosophy.

1. What the Original Spec Got Right
The proposal → validation → maintainer review → merge model, framed as "exactly like a pull request," is the correct trust mechanism and is kept as designed. The gap is that the original doc describes the workflow but not the roles, abuse handling, or rollout sequencing needed to actually launch it safely.
2. Phased Rollout (Not All-At-Once)
Phase
What's live
Why sequenced this way
v0.1
Read-only site. Anonymous "report an issue" form only — flags a field as disputed, doesn't propose a replacement value.
Zero moderation infrastructure needed; still gives maintainers a signal on which fields are wrong without exposing an edit surface to abuse.
v0.1.5
"Report an issue" form upgraded to accept a suggested replacement value + source URL, still requires no account.
Low-effort way to start collecting real correction data before building full account/role infrastructure.
v0.2 / Phase 3
Full account system, edit_proposals workflow, maintainer review queue UI, version history visible on model pages.
Only worth the build cost once there's a userbase and enough traffic that self-service moderation actually saves more time than it costs.
Why this matters:  The original doc's full workflow (roles, proposals, merges, version history) is a real project in itself — comparable in scope to the core catalog. Building it before the catalog has traffic means building moderation tooling for a community that doesn't exist yet. Sequence it after v0.1 proves people actually want the product.
3. Roles

Permissions
Viewer (default, no account)
Browse, search, compare, submit anonymous "report an issue"
Contributor (registered account)

6. Abuse & Spam Handling (Missing from Original Spec)
Rate-limit anonymous submissions per IP (v0.1/v0.1.5) — e.g. max 10 report submissions per hour per IP, generous enough for genuine use, tight enough to blunt scripted spam.
Registered-account proposal rate limits scale with reputation — new accounts capped low (prevents mass fake-account submission floods), track record raises the cap.
Any proposal that would change a field already at official or verified level requires a stronger justification bar (a live source URL check, not just free text) before it's even queued for maintainer review — makes it harder to bury a false correction to a well-verified field among a batch of legitimate ones.
Self-submitted model entries (an organization or developer adding their own model) are flagged distinctly in the UI ("submitted by creator") rather than blended in as anonymous community data — transparency about self-interest, not a ban on it.
7. Rollback & Audit
field_history is append-only and never edited/deleted — it is the audit trail the trust model depends on.
Any maintainer can revert a field to a prior field_history value in one action; the revert itself is logged as a new history entry, not a silent rewrite.
Admins can review a per-user contribution history to catch a bad-faith account operating across many small "reasonable-looking" edits rather than one obvious act of vandalism.
8. What Was Deliberately Left Out
Public leaderboards for top contributors — gameable and encourages volume over accuracy; if added later, weight it by approval rate, not raw submission count.
Full wiki-style direct-edit-then-review-after model (edit goes live immediately, gets reverted if wrong) — too high-risk for a product whose entire value proposition is data trustworthiness; propose-then-review is slower but correct for this specific use case, unlike a general wiki where speed matters more.
